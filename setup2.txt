HOW GEM5 WRITES THE OUTPUT FILE, AND WHY IT FAILED BEFORE
========================================================

What exactly makes gem5 write the file?
---------------------------------------
No gem5 source modification was required for this solution. The XiangShan
gem5 checkout already implements an operation called m5_write_file. The
bare-metal application was changed to execute that existing operation.

The complete path is:

    Bare-metal application
            |
            | executes RISC-V instruction 0x9e00007b
            v
    gem5 recognizes M5OP_WRITE_FILE (function 0x4f)
            |
            | reads arguments from registers a0, a1, a2, and a3
            v
    gem5 copies bytes from simulated guest memory
            |
            v
    gem5 writes the bytes into a real host file under its -d directory

The application executes the operation with this inline assembly:

    asm volatile(
        ".4byte 0x9e00007b"
        : "+r"(a0)
        : "r"(a1), "r"(a2), "r"(a3)
        : "memory"
    );

This instruction is the RISC-V encoding of gem5's m5_write_file operation in
the gem5 fork used by this project.

Register arguments
------------------
    a0 = address of the data buffer in simulated memory
    a1 = number of bytes to write
    a2 = byte offset inside the output file
    a3 = address of the zero-terminated output filename

After the operation finishes, a0 contains the number of bytes written. The
application checks this return value against the requested number of bytes.

What gem5 does internally
-------------------------
When gem5 decodes the special instruction, its writefile() implementation:

1. Reads the filename string from simulated memory using the address in a3.
2. Reads the requested data from simulated memory using a0 and a1.
3. If a2 is zero, creates or truncates the host output file.
4. If a2 is nonzero, opens the file and seeks to that byte offset.
5. Writes the copied bytes using the host operating system.
6. Returns the written byte count to the simulated program in a0.

For a relative filename such as result.bin or T2_Sobel_output.bmp, gem5 puts
the host file inside the directory selected by its -d command-line option.
For example:

    gem5.opt -d build/my_app-m5out ...

If the application writes "result.bin", the output is:

    build/my_app-m5out/result.bin

The file is created by the gem5 host process. It is not created inside a
guest filesystem.

Why did writing fail originally?
--------------------------------
The original program used normal file operations such as:

    fopen("output.bmp", "wb");
    fwrite(...);
    fclose(...);

That works with the QEMU target because it is a RISC-V Linux application.
QEMU forwards the program's file system calls to Linux, and Linux creates the
file.

The gem5 target runs a raw bare-metal image with a command similar to:

    --raw-cpt --generic-rv-cpt=MY_APP.bin

That program does not run under Linux. It has no Linux kernel, Linux file
descriptors, or filesystem system calls. Therefore, Linux-style fopen and
fwrite cannot create a host file in this configuration.

The initial program also did not execute m5_write_file, so gem5 was never
asked to copy the output buffer into a host file.

Why are compile-time data and the memory fence used?
----------------------------------------------------
gem5's pseudo-operation reads bytes from simulated memory when the special
instruction executes. Data that is generated immediately before the call may
still be held in the simulated CPU's pending stores or cache path.

The solution uses this instruction before exporting generated data:

    asm volatile("fence rw, rw" ::: "memory");

The fence completes earlier reads and writes before gem5 copies the buffer.
Without it, the Sobel test produced a small number of pixels that did not
match the QEMU output.

The filename, BMP header, and palette are compile-time constant data. They are
already included in the loaded bare-metal image, so gem5 can read them
reliably. The calculated pixel buffer is written after the fence.

How the Sobel BMP is assembled
------------------------------
The Sobel example writes one file in three calls:

    offset 0       : 54-byte BMP header
    offset 54      : 1024-byte grayscale palette
    offset 1078    : 262144 output pixels (512 x 512 bytes)

The first call at offset zero creates or truncates the file. Later calls use
nonzero offsets, so they keep the existing contents and add each section in
the correct position. The complete file size is 263222 bytes.

For another project, the output does not need to be BMP data. The same method
can write text, raw arrays, PGM data, measurements, or any other byte buffer.
Only the file format and offsets need to match that project's output.

Summary
-------
The file-writing problem was solved by replacing Linux-style file output in
the bare-metal path with gem5's existing m5_write_file pseudo-instruction.
The application passes the filename, buffer, size, and offset through RISC-V
registers. gem5 copies the bytes from simulated memory and creates the real
file on the host under the -d output directory. Compile-time metadata and a
memory fence ensure gem5 reads complete and current data.
